1. Project Overview & Explanation

SusTally BRSR Agent is a full-stack sustainability analyst that turns SEBI BRSR/XBRL filings into a queryable knowledge base and lets users ask ESG questions in plain English.

Indian listed companies file Business Responsibility and Sustainability Reports (BRSR) with the National Stock Exchange (NSE). These filings contain greenhouse-gas emissions, energy and water use, waste, workforce diversity, board composition, and safety metrics. The raw format is XBRL/XML — useful for machines, difficult for analysts to explore interactively.

This project solves that gap. It downloads filings, parses XBRL into a structured reports table, and exposes a chat interface where a large language model (LLM) decides which database tools to call. Answers are grounded in real numbers, optionally cite PDF page sources, and can include charts for rankings and comparisons.

1.1 Problem statement

  • BRSR data is scattered across thousands of XBRL and PDF files.
  • Analysts need cross-company rankings, year filters, and sector comparisons — not one PDF at a time.
  • LLMs alone hallucinate ESG numbers; they need controlled retrieval and schema-bound rules.
  • Production use requires auth, durable chat history, and public PDF links for citations.

1.2 Solution in one sentence

Design principle. Prefer one safe SQL tool call when possible; never invent metrics or columns; cite PDF pages only when a verified page index exists; stream progress so the UI feels responsive.

2.1 Architectural style — tool-calling agent

Unlike a fixed classify → SQL → narrate pipeline, this agent gives the LLM four tools and lets it decide when and how to query. A compact system prompt keeps context small for faster inference. Guardrails in code (SELECT-only SQL, unknown-column checks, ranking sanitization, citation verification) compensate for model mistakes.

2.2 Data flow (ingest → answer)

# Offline / batch pipeline

XBRL XML     →  preprocess.js            →  reports table (SQLite/Postgres)
PDF files    →  upload_pdfs_to_hf/r2     →  public URLs + pdf_*_urls.json
PDF text     →  page-index.js            →  metric_pages_json (citations)

# Online / request path
User question → POST /api/chat (SSE)
             → runAgent() tool loop
             → enrich + optional PDF verify
             → streamed markdown answer (+ json-chart)

4. How a Query Works

End-to-end path for a typical question such as “Top 5 companies by renewable energy share in 2025”:

1

User sends the question

The UI posts to POST /api/chat with the message and recent chat history. The response is an SSE stream so status updates appear live.

2

Agent builds the LLM context

runAgent loads the compact system prompt (schema + rules), trims history to the last few turns, and registers the four tools.

3

Model chooses a tool

For rankings it typically emits one execute_sql_query call, e.g. selecting company, year, renewable_energy_share with WHERE year = 2025, non-null filters, and ORDER BY … DESC LIMIT 5.

4

SQL is sanitized and executed

Only SELECT is allowed. Company equality is relaxed to LIKE '%…%'. Unknown columns are rejected. Ranking queries are rewritten so NULL/0/invalid share rows cannot “win.” Row count is truncated for context limits.

5

Results are enriched

Rows get PDF URLs, share breakdowns (e.g. GJ renewable of GJ total), and page citations when metric_pages_json has a confident match. Progress events update the UI (“Comparing…”, “Gathered data…”).

6

Final answer is generated

The LLM receives tool output and writes a structured analysis (Executive Summary, Key Findings, Analysis, Recommendation) plus an optional json-chart block. Citations appear inline only when verified fields exist.

7

Stream completes & chat is stored

SSE sends status: done. Guests may use localStorage; signed-in users persist sessions via Firebase-backed tables. A copy may also land in data/chats.json for ops debugging.

4.1 Safety rules that shape answers

  • Schema-bound: If the user asks for a metric that is not a column (e.g. “disabled female workers”), the agent must say it is unavailable — not substitute a related field.
  • Year exactness: Asking for 2025 must not silently return 2026.
  • Citation honesty: Aggregates and sector averages never get fake PDF page citations.
  • Share display: Percentages include numerator/denominator from share_breakdown, without showing raw formulas.

4.2 Example SQL the agent might emit

SELECT company, year, renewable_energy_share,
       renewable_energy_consumption, energy_consumption
FROM reports
WHERE year = 2025
  AND renewable_energy_share IS NOT NULL
  AND renewable_energy_share > 0
ORDER BY renewable_energy_share DESC
LIMIT 5;

6. Hosting & Deployment

The app is designed for Vercel serverless hosting of agent/src/server.js, with configuration in vercel.json. Critical data files (SQLite DB when used, metadata JSON, URL maps, and the public UI) are included in the build.

6.1 Recommended production topology

Compute & API

  • Vercel Node serverless function
  • Routes: all traffic → server.js
  • On Vercel, SQLite is copied to /tmp if used

Database

  • Neon Postgres via DATABASE_URL
  • Survives serverless ephemeral disks
  • Same reports schema as SQLite

Auth & sessions

  • Firebase Authentication (client)
  • Admin SDK verifies ID tokens
  • httpOnly cookie sessions

PDF sources

  • Hugging Face Datasets (preferred free public links)
  • Cloudflare R2 as alternate
  • URL maps committed as JSON

6.2 Deployment steps (checklist)

  1. Create a Neon project and set DATABASE_URL.
  2. Run npm run migrate:postgres (or preprocess against Postgres) so reports is populated.
  3. Upload PDFs: npm run upload:hf (or upload:r2) and commit the URL map.
  4. Configure Firebase web + service account env vars and SESSION_SECRET.
  5. Set at least one LLM key (OPENAI_API_KEY or OPENROUTER_API_KEY) — local Ollama is not available on Vercel.
  6. Connect the Git repo to Vercel; env vars mirror .env.example.
  7. Deploy; verify /api/status, /api/config, sign-in, and a sample chat.

7.1 Why a tool-calling agent (not only RAG)

BRSR questions are often analytical (rank, average, compare) rather than paragraph lookup. SQL over a wide reports table answers those cleanly. Tool calling lets the model compose queries while application code enforces safety. PDF page indexing then adds transparency for single-company metric claims.

8. What I Learned from This Project

  1. Grounding beats eloquence. An LLM that speaks confidently about Scope 1 emissions is useless without a SELECT path and “never invent numbers” rules. Schema-bound prompts plus SQL column allowlists cut hallucinations more than longer system prompts alone.
  2. Tool calling needs application guardrails. Models emit exact company = 'HDFC Bank', invent columns, or rank NULL as zero. Fuzzy LIKE rewrites, unknown-column errors, and ranking sanitizers turned “almost right” SQL into trustworthy answers.
  3. Citations are a product feature, not a markdown trick. Linking to a PDF is easy; linking to the correct page requires indexing, scoring, and refusing to cite aggregates. Honesty about “no citation available” builds more trust than fake page numbers.
  4. Local vs cloud is a continuum. Ollama is ideal for iteration cost and privacy; production needs cloud models and a durable database. Designing one adapter layer (ollama-client.js, db.js) made that swap a configuration change.
  5. Streaming UX matters for agent latency. Multi-step tool loops feel slow if the UI waits for a single JSON blob. SSE progress (“Querying BRSR…”, “Gathered data…”) keeps users oriented during 5–30s runs.
  6. Evaluation is part of the system. Scripts for smoke tests, citation tests, model comparisons, and LLM-as-judge scoring made regressions visible when prompts or sanitizers changed.
  7. ESG domain knowledge belongs in the prompt and schema. Year ↔ fiscal-year mapping, intensity metrics, and share breakdowns are domain rules. Encoding them centrally (system prompt + share-breakdown.js) keeps answers consistent across models.
  8. Deployment constraints reshape architecture. Serverless filesystems are ephemeral; SQLite demos do not survive. Neon, external PDF hosting, and Firebase sessions were necessary to turn a laptop agent into a hosted product.
